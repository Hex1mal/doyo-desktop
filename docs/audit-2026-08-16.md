# Doyo Audit — 2026-08-16

Audit of Doyo Desktop at commit `f361e15` (branch `main`, working tree clean).
Scope: architecture review, correctness and data-integrity hunt, security review,
and targeted fixes. Findings are recorded whether or not they were acted on.

## 1. Baseline

The repository arrived in a healthy state. Every project-native check passed
before any change was made:

| Check                                       | Result                            |
| ------------------------------------------- | --------------------------------- |
| `npm run check` (svelte-check)              | 387 files, 0 errors, 0 warnings   |
| `npm run test:unit` (vitest)                | 13 files, 62 tests, all passing   |
| `cargo test --workspace`                    | 32 integration tests, all passing |
| `cargo clippy --all-targets --all-features` | 0 warnings                        |
| `cargo fmt --check` / `prettier --check`    | clean                             |

This matters for interpreting the findings below: none of them are the kind a
compiler, linter, or the existing suite could have caught. They were found by
reasoning about data flow and then proven with throwaway probe tests.

## 2. Architecture

The intended layering is real and, with one exception, consistently followed:

```
Svelte UI -> stores/services -> api/client.ts -> Tauri IPC -> Rust service -> repository -> SQLite
```

Observations:

- `core` is a clean library crate with no Tauri dependency; `src-tauri` is a thin
  command layer. This is the right split and makes the core testable, which the
  32-test integration suite takes advantage of.
- Node hierarchy rules (which types may parent which) are enforced in
  `NodeService::validate_parent_rule`, i.e. on the backend, not in the UI. Cycle
  prevention is likewise authoritative in the repository layer. Good.
- Import runs inside a single transaction with format and version validation and
  full ID remapping (`core/src/import/mod.rs`). Export documents in-band that it
  is not a byte-for-byte backup. Both are in good shape.
- **Exception:** property mutation pushed correctness onto the frontend. Every
  view that touched `properties.custom` had to remember to spread the existing
  object first, because the backend replaced the blob wholesale. All call sites
  happened to do this correctly, but the invariant was unenforced and one
  helper (`moveTaskDate` in `src/lib/utils/calendar.ts`) returns a bare `custom`
  object that is only safe because its two callers re-merge. See finding D1.

## 3. Development stage

**Late Beta / Release Candidate**, held back from v1.0 by the data-integrity
findings below rather than by missing features.

Evidence for maturity: comprehensive CI (secret scan, format, typecheck, unit
tests, clippy with `-D warnings`, Rust tests, production build), a real test
suite covering hierarchy/cycles/trash/import-export, transactional import,
path-traversal validation on both backups and attachments, a tight CSP, and a
minimal Tauri capability set. No TODO/FIXME/HACK comments and no stray debug
logging anywhere in the tree.

Evidence against: the restore path could destroy the user's only database
(D2), and property writes could silently discard metadata (D1). For an app whose
value proposition is "trust me with your daily work locally", those are
disqualifying until fixed.

## 4. Findings

Severity per the project's own scale. "Proven" means a probe test reproduced the
defect against the real code before any fix.

### D1 — Property writes silently destroyed unrelated metadata (P0, proven, fixed)

**Root cause.** `NodeProperties` is a fixed Rust struct. Every property write
round-tripped the whole JSON blob through it, and `map_node` swallowed parse
failures with `unwrap_or_default()`. Two consequences:

1. Any key not declared by the struct was dropped on any property write.
2. If the stored JSON failed to deserialize (e.g. a date-only `due_date` that
   `DateTime<Utc>` rejects), the node was read back as _empty_ properties, and
   the next write persisted that emptiness.

**Failure scenario.** A task carries `custom.gtdState`, `custom.eisenhowerQuadrant`
and `custom.paretoImpact` set from the GTD, Matrix and Pareto views. The user
changes its priority from the task row. Probe result before the fix:

```
stored before:  {"due_date":"...","priority":1,"custom":{"gtdState":"next","eisenhowerQuadrant":"q1","paretoImpact":9}}
after set_priority: {"priority":2}
```

Due date and all productivity metadata gone, with no error. The unknown-key case
was equally reproducible: `{"priority":1,"futureFeatureField":{...}}` became
`{"priority":3}`.

**Fix.** Property merging now happens at the JSON layer, never through the
struct. Added `read_properties_object` / `merged_properties_json` and a
`patch_properties` repository primitive that applies only the keys the caller
named (`null` clears a key). `NodeService::set_due_date` and `set_priority` now
express a single-field intent instead of rewriting the blob, and
`NodeRepository::update` merges the patch over the stored JSON. Unknown and
unparseable-but-valid keys are preserved untouched. This is the "atomic field
update" shape rather than a read-modify-write of the whole object, so the
backend now enforces the invariant the frontend was previously trusted with.

**Regression tests.** `test_property_writes_preserve_unknown_and_unrelated_keys`,
`test_unparseable_properties_survive_an_unrelated_write`.

### D2 — Restore could destroy the live database (P0, proven, fixed)

**Root cause.** `BackupService::restore_backup` was a bare
`std::fs::copy(backup -> db_path)`. It validated the _filename_ (path traversal
was correctly blocked) but never the _file_.

**Failure scenario.** Any `.db` file in the backups directory that is not a valid
Doyo database — truncated by a full disk, corrupted, copied in from elsewhere,
or written by a newer Doyo — is copied over the live database. Probe result
before the fix: restoring a file containing the bytes `not a sqlite database`
returned `Ok(())`, and the live database afterwards could not be opened at all.
Total, silent, unrecoverable loss of the user's only copy.

The `createSafetyBackupBeforeRestore` preference mitigated this but is
user-disableable and was not a guarantee.

**Fix.** `restore_backup` now, in order:

1. validates the candidate with `validate_restorable_database` — opened
   **read-only** (so validation cannot itself write to or set the journal mode of
   the file), checked for `PRAGMA integrity_check = ok`, a `nodes` table, an
   applied `schema_version >= 1`, and a version not newer than this build
   supports;
2. snapshots the live database to `doyo-pre-restore-*.db` unconditionally, so a
   restore is reversible regardless of the user preference;
3. stages the copy beside the live file and `rename`s it into place, so an
   interrupted copy cannot truncate the live database;
4. deletes the replaced database's `-wal`/`-shm` sidecars, which describe the
   _previous_ database and must not be replayed over the restored file.

Pre-restore snapshots are pruned against their own budget so a burst of routine
backups cannot evict the snapshot that makes a restore reversible. The Tauri
command returns the snapshot filename and the UI now shows it, so the user is
told exactly how to roll back.

**Regression tests.**
`test_restore_rejects_invalid_backups_without_touching_live_database` (covers
non-SQLite, valid-SQLite-but-foreign, and truncated-Doyo inputs),
`test_restore_snapshots_live_database_and_clears_stale_sidecars`.

Note: the two pre-existing backup tests asserted that restore succeeds on
arbitrary byte content (`b"original"`). That assertion encoded the bug, so both
were rewritten to use real migrated databases.

### D3 — Silent partial checkpoint before backup (P1, fixed)

`checkpoint_database` ran `PRAGMA wal_checkpoint(FULL)` through `execute_batch`,
which discards the result row. That pragma reports "busy / incomplete" in its
result rather than as an error, so a checkpoint that did not finish was
invisible — and the subsequent file-copy backup would silently omit whatever was
left in the WAL.

Fixed to read the result row, use `TRUNCATE`, and fail loudly with an actionable
message when the checkpoint could not complete.

Worth recording: an earlier probe of `BackupService::create_backup` in isolation
showed a backup missing data (50 of 51 nodes, with 4 MB sitting in the WAL
against a 278 KB main file). That is a hazard of the service used standalone, but
**not** a live defect — the Tauri command checkpoints first, and a probe faithful
to the real call sequence produced a complete backup. Reported here as a
library-level sharp edge, not as a shipped bug.

### D4 — Migrations were not atomic (P1, fixed)

Each migration ran as a loose `execute_batch` outside a transaction, with the
`schema_version` row inserted afterwards. A failure part-way through migration
001 would leave several tables created but no version recorded; the next launch
would replay `CREATE TABLE nodes` against an existing table and fail forever.
Migration 005 (`ALTER TABLE ... ADD COLUMN`) is likewise not idempotent.

Fixed: migrations are now a data table, and each runs inside a transaction that
also records its version, so a migration is all-or-nothing and a failed upgrade
leaves a cleanly retryable database. Added `LATEST_SCHEMA_VERSION`, which also
gives restore its forward-compatibility check.

### D5 — No pre-upgrade snapshot (P1, fixed)

A schema upgrade had no safety net. Added `backup_before_schema_upgrade`, which
snapshots the database into `migration-backups/` when the stored schema version
is behind this build. It truncates the WAL into the main file first, since a
plain copy of a WAL-mode database would otherwise miss uncheckpointed data. Skips
brand-new and already-current databases so it costs nothing on normal launches.

### D6 — Dependency vulnerabilities (P2, fixed)

`npm audit` reported 1 high (`nanoid`), 1 moderate (`@sveltejs/kit` content
negotiation ReDoS), 1 low (`cookie`). Resolved the high and moderate with a
non-`--force` `npm audit fix`; the change is 6 lines of lockfile and no manifest
change. Target of 0 critical / 0 high met.

Three low findings remain and are **accepted**: clearing them requires
`--force`, i.e. a breaking major bump of `@sveltejs/kit` and
`@sveltejs/adapter-static`. The vulnerable code paths are server-side request
handling, which does not exist in this application: Doyo ships a static build
(`adapter-static`) inside a Tauri webview with no server and a CSP restricting
`connect-src` to `'self'`. The risk is not reachable at runtime, and a breaking
framework upgrade before v1.0 is the larger hazard.

### D7 — Documentation overstated behavior (P2, fixed)

README described backup and restore without noting that restore was
unvalidated, and listed "Habits and Countdowns with reminders" without stating
that reminders only fire while Doyo is running. Reminders are polled in-process
about once a minute (`src/lib/stores/reminders.svelte.ts`); nothing is registered
with the OS scheduler, so a closed app delivers nothing. README now documents
both the new restore guarantees and the actual reminder behavior.

### D8 — Reduced motion not respected (P2, fixed)

No `prefers-reduced-motion` handling existed. The practical impact is small —
the whole app contains only 4 transition declarations and no keyframes — but the
guard is free and correct. Added to `src/app.css`.

### D9 — Startup panicked instead of recovering (P1, fixed)

`setup()` used `.expect()` for the app directory, legacy import, database open
and migrations. A database that could not be opened killed the process before a
window existed: no message, no way in, and no hint that usable copies were
sitting in `backups/` and `migration-backups/`.

Nothing in startup panics now. `initialize_database` tries to open and migrate;
on failure it moves the database aside — renamed into `unopenable/`, never
deleted, with its `-wal`/`-shm` sidecars kept alongside it — and starts a fresh
one so the window always appears. The failure becomes a `StartupReport` that the
UI renders as a blocking recovery screen: what happened, where the old file was
preserved, and a list of copies that pass `validate_restorable_database`, newest
first, each restorable in one click. Only candidates that actually validate are
offered. A legacy-import failure is now a warning rather than fatal, and an
unwritable data directory falls back to an in-memory database and says plainly
that changes will not be saved.

### D10 — Restore required a manual restart (P1, fixed)

Services hold an `Arc<Database>` cloned at startup, so replacing the file
underneath them left the session reading a database that no longer existed on
disk; the UI could only tell the user to restart.

`Database::reopen` swaps the `Connection` inside the existing handle, which every
clone picks up without rebuilding application state. The command sequence around
it matters: checkpoint, then `detach()` so SQLite completes its WAL cleanup
against the database it actually opened, then the file swap, then reopen,
**then run migrations** — a backup may predate the current schema — then clear
undo history, since those snapshots describe rows in the replaced database. A
failed restore reattaches to the untouched live file rather than stranding the
session on the scratch connection.

**Regression tests.** `test_reopen_activates_restored_database_for_live_services`,
`test_restored_older_schema_is_migrated_on_activation`,
`test_failed_restore_leaves_live_database_usable`.

### D11 — Calendar and timeline opened on a stale date (P2, fixed)

`calendarPrefs.currentDate` was persisted to localStorage and restored verbatim,
so Doyo opened on whichever month was last viewed. Observed live: the calendar
showed July 2026 on a launch in August 2026. Which date you are looking at is a
position, not a preference; it now always starts on today, while view mode, week
start and show-completed stay persisted.

**Regression test.** `src/lib/stores/ui-prefs.test.ts` — verified to fail against
the previous behaviour before the fix was kept.

### D12 — UI hierarchy and repetition (P2/P3, fixed)

Found by driving the running app rather than reading `app.css`. The token system
was already sound; the problems were hierarchy and repetition, and they repeated
on every screen. Details in section 8.

## 5. Reviewed and found sound

Recording these so a later reader does not re-litigate them.

- **Security.** No `{@html}`, no `innerHTML`, no arbitrary URL/file opening
  anywhere in the frontend — the XSS and untrusted-navigation surface is empty.
  CSP is restrictive and does not use `unsafe-inline` for scripts in production.
  Tauri capabilities are minimal (`core:default`, webview zoom, notifications) —
  no filesystem or shell plugin is exposed. Path traversal is validated on both
  backup names and attachment paths, each with a test. No secrets in the tree;
  gitleaks runs in CI with a justified allowlist covering only localStorage key
  names.
- **Import/export.** Transactional, format- and version-gated, remaps IDs,
  dedupes tags by name, validates the destination parent. Round-trip covered by
  `test_json_export_import_nested_hierarchy_round_trip`.
- **Rust panic surface.** The high `unwrap()` count is almost entirely
  `column_index("...").unwrap()` against literal column names in queries that
  select them — not a realistic panic. `map_node` degrades rather than panics.
  The startup `expect()` calls remain (see remaining work).
- **Design system.** `src/app.css` already defines 56 tokens covering a
  typography scale, spacing scale, semantic surfaces, a three-level text
  hierarchy, accent, semantic status colors, borders and priority colors, with a
  complete dark-theme override. Only 21 hardcoded hex values leak across 34
  components. This is closer to what sections 19–20 of the brief ask for than to
  an "assembled" UI; a wholesale restyle is not warranted.
- **Focus indicators.** The nine `outline: none` declarations were checked
  individually. Each is paired with a visible replacement (`:focus` border plus
  box-shadow ring, `:focus-visible` accent background, or a persistent accent
  border on inline edit inputs). No accessibility regression here.
- **Settings sources of truth.** Deliberately dual: SQLite is authoritative,
  localStorage is a documented fallback for when the backend is not yet ready.
  The code comments say so explicitly. Not a bug; noted as a design decision.

## 9. Pre-release verification

### D13 — `replace_properties` deleted keys it did not model (P1, proven, fixed)

Audited all three frontend call sites of `nodeReplaceProperties`: the generic
`replaceProperties`, `setColor` (tree and sidebar context menus) and
`saveScheduling` (the due-date dialog). All build their replacement from
`{...node.properties}`, and the store's copy comes from `normalizeProperties`,
which constructs an object with exactly the eleven modelled keys. Any other key
in the stored blob is therefore absent from the replacement and was erased.

Two of the three are ordinary user actions, so this was reachable by picking a
node colour. Proven before fixing: a colour change turned
`{"priority":1,"custom":{...},"futureFeatureField":{"keep":"me"}}` into
`{"priority":1,"custom":{...},"color":"#336699"}`. `custom` is modelled, so GTD,
matrix, kanban and Pareto metadata were never at risk — only keys this build does
not know about, i.e. anything written by a newer build.

**Verdict: it was not safe, and is now bounded rather than removed.** Replace is
still a genuine replace over the keys `NodeProperties` can describe, which is what
makes clearing a field work; it no longer touches anything else.
`KNOWN_PROPERTY_KEYS` records the boundary and
`test_known_property_keys_match_the_struct` fails if a field is added to the
struct without being listed.

### D14 — Stale-snapshot races in custom metadata (P2, fixed)

`mergedCustom` (nodes, calendar) and `mergeCustomStatus` (kanban) merged a change
over the store's copy of a node and sent the whole `custom` bag back. Sites:
Kanban drag and status rename, calendar drop, GTD, matrix, Eat the Frog, Pareto,
won't-do, task conversion, node config. Each view owns a few keys and knows
nothing about the others, so two edits racing on stale copies could silently
revert one another — and the merge base was only as fresh as the last `upsert`.

Fixed by construction rather than by tightening the merge: a `node_patch_properties`
command applies named keys against the **stored** value, `null` clears a key, and
`custom` merges by sub-key. Every custom-writing flow now names only what it
changes. `setColor` and `saveScheduling` moved onto it too, so neither sends
priority or custom at all. `mergedCustom` and `mergeCustomStatus` were deleted
along with the responsibility they carried.

**Verdict: the class is closed.** No frontend flow now sends a property snapshot.

### D15 — `get_full_tree` was quadratic (P0, proven, fixed)

The query the whole UI loads from walked down from the roots with a recursive
CTE. `EXPLAIN QUERY PLAN` showed the recursive step as a search on
`idx_nodes_deleted_at` — which matches nearly every row — followed by
`SCAN ft`, a full scan of the working table: a nested loop.

|  nodes | recursive CTE | flat query | same rows |
| -----: | ------------: | ---------: | :-------: |
|  1,000 |        100 ms |       0 ms |    yes    |
| 10,000 |     11,383 ms |      20 ms |    yes    |
| 50,000 |    312,945 ms |      45 ms |    yes    |

For the whole tree the walk is also unnecessary: soft delete cascades to
descendants and hard delete cascades by foreign key, so no live node can have a
dead ancestor and "reachable from a root" is exactly "not deleted". Verified
equal at every size. Callers sort children by position themselves, so the CTE's
depth ordering was not load-bearing.

This mattered beyond startup — `nodeStore.load()` runs after many operations, so
at 10k nodes the UI would have frozen for eleven seconds repeatedly.

### Performance smoke, after the fix

Backend query timings, release build, against generated hierarchies with due
dates, priorities, completion and custom metadata:

| Operation                         | 1,000 nodes | 10,000 nodes |
| --------------------------------- | ----------: | -----------: |
| open + migrate                    |        1 ms |         1 ms |
| `tree_get_full` (startup payload) |        5 ms |        67 ms |
| Today                             |        1 ms |        11 ms |
| Overdue                           |        3 ms |        26 ms |
| Search (FTS)                      |        6 ms |        13 ms |
| Quick find                        |        0 ms |         3 ms |
| Node count                        |        0 ms |         0 ms |
| Database file                     |      1.0 MB |       7.7 MB |

Before the fix the same startup payload took 127 ms and 22,570 ms.

**Not measured:** frontend render cost at 10k nodes. These are backend query
timings only. Several views project the full node set in `task-projection.ts`,
and whether that stays responsive at 10k rows is unverified — see remaining work.
